## 第一部分 · 整体地基

### 1.1 分层结构

整个系统是四层，**每层只做自己的事，不越界**：

| 层 | 位置 | 职责 | 规模 |
|---|---|---|---|
| 内核 | `src/kernel/`（29 个模块） | 机制：消息怎么进、怎么判、怎么发、怎么存 | 10454 行 |
| 协议端 | `src/transports/onebot/` | 怎么跟 QQ 说话（可替换） | 358 行 |
| 控制台 | `src/console/`（13 个适配器）+ `ui/panels/` | 人机界面 | — |
| 插件 | `bundled/`（10 个） | 业务：具体能干什么 | 979 行 |

**关键设计：内核不认识"业务"。**

内核里搜不到任何 `market`、`community`、`model-prices`、`telemetry` 这类词——它们全在 `src/console/` 的适配器里。内核只提供机制，"社区市场怎么用""价格从哪来"这类问题内核不关心。

这带来一个直接好处：**换业务不用动内核**。加功能就是加一个插件文件。

### 1.2 一句话概括每层怎么工作

**内核**：`onIncoming` 收到一条消息 → 交给 `ingest` 清洗准入 → 交给 `wake` 判断该不该回 → 该回就交给 `orchestrator` 建会话跑 LLM 循环 → `send` 队列按限频发出去 → `store` 留档。

**协议端**：内核不认识 OneBot。所有 QQ 相关操作都走 `transport` 契约（`connect` / `on` / `call` / `stop` 四个方法）。协议端差异由 provider 处理，内核只依赖传输契约。

**控制台**：HTTP 服务 + SSE 推送 + 8 个 iframe 沙箱面板。每个面板是独立文档，用 `postMessage` 和外壳通信，只能调自己 manifest 里声明过的 API。

**插件**：每个插件是个目录，含一个 `skill.json`（声明元信息）+ 一个 `index.js`（导出 `setup(ctx)`）。启动时逐个装载，调用 `ctx.registerTool()` 注册工具。

## 第二部分 · 消息链路

### 2.1 一条群消息的完整旅程

```
OneBot WS 事件
    ↓
ingest（清洗准入）
    ├─ CQ 码清洗、@ 三态判定、拍一拍识别
    ├─ 白名单/黑名单/屏蔽名单过滤
    └─ 不合格 → 直接丢弃
    ↓
store.append（留档）
    └─ 原子写：写 .tmp 再 rename，断电也不会写坏
    ↓
onIncoming（是否唤醒）
    └─ 见第三部分「四档唤醒」
    ├─ 不该回 → 当场标已读，沉历史，零 token
    └─ 该回 ↓
scheduleWake（防抖倒计时）
    └─ 默认 2000ms，固定不重置（窗口内新消息只入库）
    ↓
wake（建会话跑 LLM）
    ├─ 各种闸门：暂停？模型没配？被禁言？并发满？
    ├─ 取触发批（verified批 / 机械批 / 活跃期）
    ├─ 档位固定（复用首次判定结果，不重掷骰子）
    └─ agent-runner 循环：prompt → LLM → 工具 → 结果 → 再 LLM
    ↓
send（发送队列）
    ├─ 每会话串行（同一群不会乱序）
    ├─ 分钟/小时双限频
    ├─ 去重窗口（相同文本不重复发）
    └─ 真人化停顿 + QQ 硬长度切分
    ↓
store（留档）+ sessions（会话状态收尾）
    ├─ 发过消息 → done
    ├─ 没发消息 → noreply（正常选项，不是错误）
    └─ 还有未读 → drainDelay 后再跑一轮
```

### 2.2 关键机制细节

**无状态会话（成本控制的核心）**

每次唤醒都**新开一个独立会话**，提示词 = 静态系统提示 + 存档摘要 + 本次新消息。会话结束即弃置，LLM 层面零历史。

所以每次处理的 token 成本是恒定的小份，**不随聊天量膨胀**。这是 2,256 个实例跑出来的核心卖点。

处理期间新来的消息只写存档；本次结束后发现有未读 → 自动再开新会话，直到清空。

**防抖固定不重置**

倒计时期间（默认 2 秒）新消息进来**不重置倒计时**，只入库。这样一批消息聚成一次处理，不会每条都烧一次 token。

**触发批的两种来源**

- **verified 批**：onIncoming 判定该回的那条消息所在时间窗之后的全部未读
- **机械批**：drain / 积压恢复 / 重试排的，需要**逐条补判定**（跟 onIncoming 同口径）找最早触发的那条。全不触发 → 全部标已读、干净消失、不调 LLM

**已发不重试（R-08）**

会话失败重试有个硬条件：`session.sent` 为空才重试。**发过消息绝对不重试**——否则会重复发言刷屏。

## 第三部分 · 四档唤醒

> 这是整个系统最核心的行为逻辑，也是 2,256 个实例 / 47 亿 token 调出来的护城河。
> **2026-10-06 由用户钦定权威口径**，已写入 SPEC §6.4。

### 3.1 权威定义

```
1 档：被 @ 才响应。
2 档：被 @ 或命中关键词 → 响应。
3 档：被 @ 或命中关键词 → 响应；
      否则骰一次，落在设定的概率内 → 响应；
      没命中 → 这条消息置为已读，看后续群友发言。
4 档：有消息就回。
```

**核心不变量：一条消息在整条判定链上最多只骰一次。**

### 3.2 判定的执行顺序

判定**从上往下短路，命中即止**——不是逐档下探：

```
私聊？ → 恒响应，直接返回（不看档位）
  ↓
被指令禁言？ → 强制降到 1 档
  ↓
4 档？ → 无条件响应
  ↓
被 @ 或拍一拍？ → 响应（不分档位，1/2/3/4 都算）
  ↓
2 档及以上，命中关键词？ → 响应
  ↓
3 档？ → 骰一次
  ├─ 命中概率 → 响应
  └─ 没命中 → 不响应（这条置已读，等下一条）
  ↓
1 档？→ 不响应
```

### 3.3 三个必须记住的规则

**① 1 档和 2 档绝不掷骰**

即使概率设成 100%，1 档和 2 档也**一次骰都不掷**。只有 3 档才有随机这回事。

（测试里专门断言了这条：`1 档即使概率 100 也不掷骰`）

**② 命中确定性信号时不掷骰**

3 档下如果被 @ 了、或命中关键词了，**直接响应，不掷骰**。骰子只在"没被 @、没命中关键词"这个唯一的场景下才需要。

**③ 没命中就置已读，等下一条**

不追问、不重掷、不攒着。骰子结果由 `reason` 字段带回，固定到 `session.contextReason`，会话页能看到"为什么当时没响应"。

### 3.4 拍一拍不分档位

拍一拍是"轻量召唤"，跟 @ 同级——**任何档位下都触发**。

这是个曾经踩过的坑：老实现把拍一拍塞在"1 档分支"里，结果 3 档下拍一拍不响应，机器人被拍了还装死。

### 3.5 @ 判定以 QQ 号为准

`isAtMe` 三种写法都能识别：

| 写法 | 例子 | 匹配方式 |
|---|---|---|
| @ 昵称 | `@鲸鱼酱` | 文本包含 |
| @ 机器人名 | `@小鲸鱼` | 文本包含 |
| CQ 码 | `[CQ:at,qq=20001]`（合成示例） | **按 QQ 号精确匹配** |

**为什么强调 QQ 号**：群里可能有群友跟你重名。文本匹配会误判（@ 的是同名的另一个人），QQ 号不会。

老存档没有 `atMe` 标记时，才回落到文本匹配（重名仍会误判，这是已知的历史局限）。

### 3.6 关键词要剔除 @ 片段

判定关键词前，先把 `@某人` 这部分剥掉。

**为什么**：如果词表里有"鱼"，而你 @ 了一个叫"摸鱼小能手"的群友——这明显不是在叫机器人，不该触发。

剥除规则：`atNames` 里有精确名字就用精确剥，没有就粗剥 `@` 后 1~24 个非空白字符。引用块 `[引用 ...]` 也整块剥掉（支持嵌套方括号）。

### 3.7 档位钳位

配置值会钳到 `[1, 4]` 并四舍五入：

| 输入 | 实际档位 |
|---|---|
| 0 | 1 |
| -5 | 1 |
| 2.4 | 2 |
| 2.6 | 3 |
| 99 | 4 |
| `"abc"` / `undefined` | 4（未设置） |

**坑**：不能写 `Number(x) || 4`——`0` 是 falsy，会被吞成 4 档。必须先判断是不是有效数字再钳位。

### 3.8 骰子只掷一次的工程实现

这条不变量在代码里怎么保证？判定链有三个地方会判定：

| 时机 | 做法 |
|---|---|
| onIncoming 首次判定 | 掷骰，把 `{tier, reason}` 写进 `entry._tier` / `entry._reason` |
| 机械批补判定 | 掷骰，把结果写进 `m._tier` / `m._reason` |
| 建会话时档位固定 | **不掷骰**，直接读 `entry._tier` / `entry._reason`；只在没有既定结果时才兜底重算 |

为什么要这么设计？因为判定和建会话之间有一段时间差（要走完建会话流程）。如果在固定阶段重掷，同一条消息可能"判定时说触发、建会话时说没触发"，会话页显示的原因和真实原因就对不上了。

## 第四部分 · 29 个工具的实现逻辑

工具分 6 类，分布在 10 个插件里。**工具 id 前缀规则**：捆绑插件用裸 id（`send_message`），用户插件自动加 `<插件id>__` 前缀（`mytool__search`）——这样两个插件有同名工具时互不干扰。

### 4.1 messaging · 消息类（4 个，core-tools）

#### `send_message` · 在当前会话发言
**逻辑**：把文本发到触发批所在会话。
- 传字符串 = 发一条；传数组 = 拆成多条（每个元素是**一条完整消息**，不是同一句的分段）
- 支持 @ 人（`atUserId`）、引用（`replyToMessageId`）
- 优先用会话注入的 sender（可测可替换），回落内核依赖
- 发完把内容记进 `session.sent`——**这是"已发不重试"的判据**

**权限**：`qq.send`

#### `send_to` · 跨会话发送
**逻辑**：发到另一个群或私聊。**三重校验**：目标必须在白名单 + 全局开关 `tools.crossChatSend` 必须开 + 工具本身默认关闭。
**为什么这么严**：跨会话发言是社交敏感操作（机器人跑去别的群说话），默认必须关。

**权限**：`qq.send`

#### `send_poke` · 拍一拍
**逻辑**：群聊必须传 `targetUserId`（QQ 的拍接口要求），私聊可省。

**权限**：`qq.send`

#### `finish` · 结束本轮
**逻辑**：告诉 LLM"这轮到此为止"。这是给模型的选择——`send_message` 之后再 `finish`，或想延续话题就带 `activeTopic`（≤60 字）。

**没有 finish 会怎样**：工具循环会一直转到 `maxRounds`（默认 12 轮）才停，白烧 token。

### 4.2 sticker · 表情类（4 个，sticker-tools + core-tools）

#### `send_sticker` · 发一张表情
**逻辑**：从表情库挑一张发出去。**一条消息只能是一张表情，不能附带文字**——想说的话先用 `send_message` 单独发。
**为什么限制**：QQ 表情消息的协议限制，带文字表情会显示异常。

#### `collect_sticker` · 收藏表情
**逻辑**：根据已安装的收藏能力处理消息中的图片/表情及简短备注；没有相应外部能力时，不承诺 QQ 账号侧收藏成功。
**为什么要备注**：备注是未来的自己看的——下次选表情时靠备注判断"这张适合什么场合"。

#### `list_stickers` · 查表情库
**逻辑**：列出所有收藏的表情，含备注、笔记、标签、使用次数。
**使用次数的价值**：能看出哪些表情是常用款，冷门表情可以清理。

#### `get_sticker_image` · 看表情图
**逻辑**：返回某张表情图的内容（模型能直接看懂）。

**外部收藏能力边界**：默认不提供 QQ 收藏表情同步或账号侧收藏写入。相关能力可由用户安装的独立扩展提供，接口和支持情况由扩展决定；缺少能力时不得把本地缓存或索引更新报告为 QQ 收藏成功。本地已有表情索引与读取能力保留。

**表情积极程度（0~3 档）**：不鼓励 / 偶尔 / 较积极 / 表情包爱好者。这是**提示词层面引导**，不强制——告诉模型"现在可以多用表情"，但它可以不听话。

### 4.3 query · 查询类（7 个，query-tools）

全部只读，给模型"了解当前会话"的能力。

| 工具 | 逻辑 |
|---|---|
| `get_recent_messages` | 查比【已读信息】更新或更老的消息。**权限 `data.sessions.read`** |
| `read_forward` | 展开合并转发的全文（QQ 的合并转发是嵌套结构，需要递归展开） |
| `get_active_members` | 最近谁在说话，发言数排行 |
| `get_chats` | 列出所有群/私聊，含未读数和最近一条。**跨会话发送前用它查目标** |
| `get_message_detail` | 按消息 id 查完整内容（含媒体、引用） |
| `get_message_images` | 看消息里的图片（模型能直接看懂，需要视觉模型） |
| `read_video` | 读视频：元信息 + 按视频模式给画面（抽帧） |

**为什么需要这一类**：模型光靠提示词里的【已读信息】不知道刚才谁说了什么。这组工具让它能主动查——"刚才谁问的那个问题是什么来着"。

### 4.4 memory · 记忆类（3 个，memory-tools）

#### `memory_append` · 记印象
**逻辑**：记录对某位群友的长期印象——说话风格 / 爱玩的梗 / 雷点 / 身份关系。
**关键约束**（写在工具描述里给模型看）：**只记以后打交道还用得上的**。不记"他今天说了一句你好"这种垃圾。

#### `memory_query` · 查印象
**逻辑**：查当前会话对群友的长期印象，可按 QQ 号过滤。

#### `memory_remove` · 删印象
**逻辑**：删一条过时或不再准确的印象。
**为什么需要删**：印象会过时（人换了工作、退了群）。没有删除机制的话，错误印象会一直污染对话。

#### 记忆自动整理（✅ 已实现）
设计是：后台静默跑，合并重复、删过时，冷却 6 小时。
**现状**：`kernel.js` 已以 kernel 身份注册 `memory.consolidate` 能力（`capability.register('memory.consolidate', 'kernel', ...)`），
由 LLM 整理印象并返回结构化 JSON；prompt 明确约束「不得新增事实 / 不得删除仍有用的信息 / 合并重复 / 删过时 / 每条 ≤120 字 / 保留 userId 与 name」。
控制台的手动整理按钮即消费该能力。若某个能力提供方缺席，会返回 503 并提示原因——
这是插件化架构的预期行为（能力可被其它 provider 覆盖），不是缺陷。

> 2026-10-06 修正：本节原写"还没做 / 需要插件提供"，与实现不符（能力已内置于 kernel）。
> 同时修掉了 prompt 拼接曾用字面 `\n`（双反斜杠）而非真实换行的问题——代码不报错但会把 prompt 压成一行，
> 由 `test/65-prompt-newline-test.mjs` 按"源码反斜杠个数"锁死。

### 4.5 web · 联网类（3 个，web-tools）

全部走 `safe-fetch`，**逐跳 SSRF 校验**。

#### `web_search` · 联网搜索
**逻辑**：默认 Bing，返回标题/URL/摘要。内置 6 家搜索服务（含免 Key 的 Bing 网页解析），用户可自己加任意兼容搜索服务。

#### `web_fetch` · 读网页
**逻辑**：只读抓取网页正文，≤2 万字符。

#### `search_images` · 搜图片
**逻辑**：搜网图并给出**能直接发的图片直链**（配合 `send_image`）。

**SSRF 防护（安全关键）**：`safe-fetch` 做三件事——DNS 解析后校验 IP 不是内网地址、把 IP 固定住防 DNS rebinding、手动处理重定向（每跳都重新校验）。图片地址禁内网。

**为什么这么严**：如果不做防护，一个恶意网页可以让机器人访问 `http://192.168.1.1/`（你家路由器）或云元数据接口 `169.254.169.254`（偷云凭证）。

**权限**：`net.outbound`

### 4.6 media · 媒体类（1 个，media-tools）

#### `send_image` · 发图片
**逻辑**：把网上找到的图片发到当前聊天。**四道防护**：预览优先（先给你看，你确认才发）、单次上限、字节校验、浏览锁定白名单免预览。
**权限**：`qq.send` + `net.outbound`

**为什么预览优先**：发错图到群里是社死事件。让模型（和用户）过一道眼。

### 4.7 system · 系统类（6 个）

#### `set_reminder` / `list_reminders` / `cancel_reminder` · 提醒闹钟
**逻辑**：`set_reminder` 设定时提醒，到点机器人在当前群主动发消息。存本地文件，`scheduler` 定时器到点触发。
**用途**：群里有人喊"明早八点提醒我上班"，机器人真的能在明早八点@他。

#### `check_holiday` · 查节日
**逻辑**：查今天/最近的中国法定与常见节日，含参考祝福语。
**用途**：让机器人在中秋/春节主动在群里发祝福，而不是等别人问。

#### `report_feedback` · 反馈问题
**逻辑**：向管理员反馈问题或建议。**明确标注"不用于聊天"**——防止模型误用它当聊天工具。

### 4.8 两个特殊插件

#### `hello` · SDK 活样例
**逻辑**：注册一个 `hello_say` 工具 + 一段提示词片段 + 命名空间存储。**它是"捆绑插件怎么写"的参考实现**，默认停用。
**看它就知道**：一个插件最少需要写什么。

#### `mcp-bridge` · MCP 桥接
**逻辑**：通过受权限管控的 stdio MCP 客户端发现并调用外部工具。让 0.5 能用上其他 MCP 服务器提供的工具。
**权限**：`proc.exec` + `mcp.connect`（这两个权限给得很重，因为 MCP 客户端能启动外部进程）
**扩展价值**：这是"接外部生态"的口子——理论上接一个 MCP 服务器就能加一批工具。

#### `compat-04` · 0.4 插件兼容垫片
**逻辑**：把 0.4 的 `createSkillApi` 调用映射到 0.5 的 SDK，让 0.4 社区的插件能直接跑在 0.5 上。
**权限映射策略**：`web_fetch` → `net.outbound`（受控）；`proc.exec` / `net.raw` / `mcp.connect` **永不映射**（安全基线优先）。
**意义**：这是"追加文件即可替换旧核心"的最终证明——老的插件生态不用重写。

## 第五部分 · 控制台面板

控制台是**零框架原生 HTML/CSS/JS**，明暗双主题 + 跟随系统。每个面板是一个独立 HTML 文档，跑在 `sandbox='allow-scripts'` 的 iframe 里。

### 5.1 面板与职责

| 面板 | 干什么 | 关键能力 |
|---|---|---|
| **会话** | 看所有会话：等待中/运行中/完成/失败 | 重试、终止（AbortController 立即断在途请求）、清已完成、看会话详情 |
| **聊天** | 存档浏览：群/私聊、消息记录 | 标已读、清空、**测试发送**、静音、按会话删消息 |
| **记忆** | 群友长期印象管理 | 查看/编辑/删除、**手动触发整理**、给单个群友更新记忆 |
| **用量** | token 和成本统计 | 按天/按会话/按模型三个维度，缓存命中率、峰谷分时计价、图片计费口径 |
| **技能** | 插件列表 + 启用停用 | 重扫磁盘、**宿主授权**（非沙箱警示）、**工具 id 冲突提示** |
| **插件** | 同技能页（内容镜像） | 同上 |
| **设置** | 所有配置项 | 动态表单（按 configSchema 生成）、脱敏显示、离页自动 flush |

### 5.2 面板安全模型（这是重点）

**双重隔离**：

1. **manifest 白名单**：bundled 面板只能调 `manifest.json` 里声明过的 method + path。未声明直接返回 `FORBIDDEN`。
2. **sandbox iframe**：面板跑在 `sandbox='allow-scripts'` 里，opaque origin，**拿不到 token**。

**用户面板更严**：用户提供的面板只允许调三个方法——`ctx.call`（调自己的工具）、`ctx.getConfig`（读自己声明的配置）、`ctx.notify`。**任何 `/api/*` 直接调用一律拒绝**。

**token 隔离**：控制台 token 从不放在 URL 里（`loadURL` 永不携带），通过 preload 的窄 IPC 一次性取。SSE 和 token 都不传入用户 iframe。

**资产校验**：面板资产只服务专用 `ui/` 目录，每个请求核验 active 状态、`ui.panel` 权限、**代际**（generation）和 realpath 真实路径。

### 5.3 设置页的动态表单

设置页不写死表单——读 `configSchema` 自动生成。好处是加一个配置项，UI 自动就有了。

**离页 flush**：改设置后切页才真正保存（防抖 + flush），避免打字过程中反复写盘。

## 第六部分 · 扩展系统

> 核心理念（用户钦点，贯穿全部设计）：**追加文件 = 改前端 / 加功能 / 换核心 / 换协议端。没有任何东西是写死的。**

### 6.1 五种扩展方式

| 需求 | 怎么做到 |
|---|---|
| 改前端页面 | 面板协议（iframe 沙箱）+ 插件 `ui/` 目录 |
| 加功能 | 插件调 `ctx.registerTool()` |
| 改核心行为 | hook（`before-llm-messages` 改消息、`before-tool` 否决）+ capability 替换 |
| 换协议端 | 换兼容的 OneBot provider 插件 |
| 跑 0.4 老插件 | `compat-04` 垫片翻译旧 API |

### 6.2 插件的生命周期

```
register → activate → ... → deactivate → dispose
```

- **禁用一定调 deactivate**——否则定时器和监听器泄漏，变成"幽灵行为"（关了插件但它还在跑）
- 覆盖注册（热重载）走完整周期：先 deactivate 再 dispose
- dispose 兜底清理该插件注册的所有工具

### 6.3 两个插件 API

**`ctx.registerTool(def)`** · 注册工具

声明：id（`[a-zA-Z0-9_-]{1,64}`）、name、description（**给模型看的提示词**）、category、params（JSON Schema）、scopes（权限）、execute（执行函数）。

**id 命名规则**（防冲突的关键设计）：
- 捆绑插件 → 裸 id（`send_message`）
- 用户插件 → 自动加 `<插件id>__<toolId>` 前缀（`mytool__search`）

这样两个插件都注册 `search` 也能共存，模型能看到两个工具、分别调用。

**`ctx.prompt.add(section)`** · 追加提示词片段

**注意：只能追加，不能覆盖核心规则。** 优先级上限 99（硬编码双重保护），核心规则由 `prompt.js` 独占先写入。同优先级按插入顺序稳定定序。

### 6.4 三个扩展点

| 扩展点 | 时机 | 能做什么 |
|---|---|---|
| `capability` 注册 | 任意 | 提供一个能力给内核或其他插件消费 |
| `hook` 注册 | 五个时序 | 前后加工消息、否决工具调用、观察响应 |
| `panel` 声明 | 启动 | 提供自己的 UI 面板 |

### 6.5 冲突仲裁（两个插件改同一处时）

| 场景 | 机制 | 谁赢 |
|---|---|---|
| 工具同名（用户插件） | id 前缀隔离 | 物理隔离，共存 |
| 工具同名（捆绑域） | 后注册者覆盖 + 警告 + 留痕 | 后加载者（可查） |
| 能力（6 个多提供者） | `claim()` 协商：返回非 null 即认领 | 按声明顺序第一个认领者 |
| 能力（其余单提供者） | `consume()` 取第一个 | 装载顺序第一个 |
| 提示词片段 | 并置非覆盖，priority 封顶 99 | 都生效，核心恒最后 |
| hook | 串行遍历 + 否决权 | 按装载顺序叠加 |

**6 个天生允许多提供者的能力**：模型请求参数、响应转换、用量统计、重试建议、工具守卫、媒体下载。

**为什么它们允许多个**：这些是"链式加工"型能力——每家管一段，返回 null 表示"不归我管"，下一个接手。比如 B 站和抖音的媒体下载插件可以共存，认领自己认识的链接。

**装载顺序** = 目录名 `sort()`。同 owner 重复注册 = 热重载路径（不算冲突）。

### 6.6 插件的删除、安装与热更新（2026-10-06 新增）

技能页和插件页签现在有三个新动作。

#### 删除插件

**三重闸门**（缺一不可）：

1. **拒删捆绑插件** —— bundled 随程序分发，删了下次升级会被打回。
2. **拒删运行中的插件** —— 正在运行的插件直接删目录会留下幽灵定时器和监听器（"关了但还在跑"）。必须先停用。
3. **路径复核** —— 目标目录必须 realpath 后仍在用户插件目录内，防路径穿越。

删除时同时清掉配置里的孤儿开关和设置。

#### 安装插件（从 ZIP）

走**和市场同一套**的受限解压逻辑（受限解压 + 声明与本地头一致性校验 + CRC 校验），不自造解压。

安全约束：包大小上限 8MB、skillId 格式校验、目标已存在则拒绝（不覆盖）、**解压失败清干净半成品目录**（不留装了一半的插件）。

#### 热更新（改代码不用重启进程）

**难点在ESM 模块缓存**：入口文件能靠 `?v=指纹` 破缓存，但插件内部的 `import './helper.js'` 不带 query，第二次 import 会直接复用旧模块——导致"外层是新代码、内层还是旧代码"的半新半旧状态。

**保守默认**：常规重载时，依赖图变了**故意报错要求重启进程**。宁可让用户重启，也不加载一半新一半旧的代码。

**热更新模式**：显式开启后，给整个依赖图换一个新的 import 命名空间（`?v=指纹&ns=随机UUID`），让所有相对 import 都解析到新 URL，真正加载新代码。

**安全约束**：指纹变化 = 代码换了 → **旧授权立即作废**，必须重新授权。这防止"改完代码沿用旧授权"——否则等于绕过授权机制偷跑新代码。

### 6.7 工具可用性判定（唯一口径）

一个工具能不能用，八层短路检查，**顺序固定**，返回具体原因：

1. 工具系统总开关
2. 所属插件是否 active
3. 硬依赖能力是否可用
4. 分类开关
5. 单工具 override / 默认关闭
6. 跨会话发送闸
7. 视觉/搜索前置（模型不支持图片时自动禁用看图工具）
8. `tool.guard` 运行时否决

**为什么要有唯一口径**：早期版本这些条件散落在 orchestrator 和 routes 两处，各判一半，出现过"UI ��能用、运行时是空工具列表"的割裂。现在只有这一处判定，控制台和运行时复用同一个函数。

## 第七部分 · 安全边界

### 7.1 权限体系

11 类权限 scope，分四档：**allow / deny / ask / 未决定**。

| Scope | 管什么 |
|---|---|
| `qq.send` | 发消息、发表情、拍一拍、跨会话发送 |
| `net.outbound` | 联网（搜索、抓网页、下载图片） |
| `net.raw` | 原始网络访问（**永不映射给 0.4 插件**） |
| `data.sessions.read` | 读会话历史 |
| `data.memory.read` | 读记忆 |
| `fs.namespace` | 插件自己的存储命名空间 |
| `proc.exec` | 启动外部进程 |
| `mcp.connect` | 连接 MCP 服务器 |
| `permission.ask` / `permission.decision` | 询问授权 / 授权决定 |
| `ui.panel` | 提供 UI 面板 |

**授权绑定代码指纹**：授权时把插件所有文件的 SHA-256 摘要一起绑定。**改了代码 → 指纹变 → 授权立即失效**。不能"先偷偷改代码再骗授权"。

**授权要走权限门**：setup 阶段的网络请求也要过权限检查。撤销授权后，旧的在途请求不会被放行。

**三种拒绝时机**：撤销 / 更新 / 关机——三种情况旧请求全部 fail-closed。

### 7.2 密钥保护

- 配置接口返回**脱敏**值（`sanitizeConfigForApi`）
- 读明文密钥需要**独立的白名单守卫**（不是通用 API 守卫）
- 控制台 token 从不放 URL，用 preload 窄 IPC 一次性取
- 窗口内所有外链交给系统浏览器，主窗口**不允许被导航离开 127.0.0.1**

### 7.3 数据安全

- **原子写**：先写 `.tmp` 再 `rename`，断电/崩溃不会写坏文件
- **读时剥 BOM**：Windows 编辑器默认写 BOM，不处理会解析失败
- **损坏当空重建**：JSON 解析失败不崩溃，当空数据重新开始
- **0.4 迁移只读**：迁移器永不回写 0.4 目录

### 7.4 成本护城河

| 机制 | 作用 |
|---|---|
| 无状态会话 | 每次处理成本恒定，不随聊天量膨胀 |
| 工具循环上限 | 最多 12 轮，到顶标记 `max_rounds` 停止 |
| 剩余轮次催发 | 剩 3 轮且还没发言 → 注入提示催模型把话说完 |
| 已发不重试 | 发过消息的会话失败不重试（防重复刷屏） |
| 触发下限频 | 分钟/小时双限频，超限直接拒绝并告诉模型 |
| 发送去重 | 窗口期内相同文本只发一次 |
| 放弃也是选项 | 没话说就 `finish`，计入 `noreply`（正常状态不是错误） |

### 8.3 明确不做的

**跨平台（微信）** —— 2026-10-04 决策删除。

**理由**（经代码核实，不是猜测）：
- 平台语义渗进三层非适配器模块：`prompt.js` 308 行含 19 处"群"、"不要当群管家"这类规则依赖 QQ 群管理员体系；`store.js` 三个方法全靠 mid 匹配；`ingest.js` 直接读 `sender.card`（群名片，QQ 独有）
- 最致命：四档概率和限频参数是 2,256 实例 / 47 亿 token 调出来的，换平台得从头调参且无先验
- "无状态会话 → 成本恒定可控"的护城河会归零

**保留**：更换 OneBot 协议端。具体接口差异与功能支持需逐项核对。

### 8.4 塞功能时的风险地图

| 方式 | 风险 | 原因 |
|---|---|---|
| **纯工具插件** | 🟢 最安全 | 走 id 前缀隔离，已实测，不碰内核 |
| **hook 扩展** | 🟡 中等 | 串行叠加 + 否决权，顺序敏感（= 目录名 sort()） |
| **碰随机档** | 🔴 已修复 | 档位重掷问题已修（2026-10-06），现在安全 |
| **碰内核模块** | 🔴 需谨慎 | 内核是所有插件的地基，改动影响面最大 |

**建议顺序**：先写纯工具插件（风险最低）→ 需要读写数据时用 capability → 最后才考虑改内核。
