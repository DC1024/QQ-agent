# 0.4模型交互的择优迁移

本记录仅对应模型子系统，完整0.4原子功能复查仍见[v04迁移计划](v04-parity-plan.md)。不以本子系统代替全部目标。

## 默认界面

- 模型目录支持手动ID、显示名称、筛选、重命名、逐项移出及磁盘保存。编辑渠道不会把既有模型对象中的能力/上下文信息退化成字符串。
- “拉取模型”先读取远端，再显示勾选弹窗；不直接把全部模型存入配置。已有条目标明且不能重复选择。勾选状态独立于当前搜索、厂商与展示页；列表每次最多展示100项，可继续展开。
- 提供主模型、记忆专用、图片、视频和备选模型的分渠道选择入口；同名ID按渠道身份区分。主模型的渠道/模型/端点一起提交，不回传宿主已有Key。记忆专用选择同时关闭“使用聊天模型”，使选定配置实际生效；图片/视频选择不擅自开启媒体输入。
- 备选选择器只编辑外层备选草稿，直到外层保存才写配置。选择保存失败只恢复该选择仍属于当前代的字段，不覆盖后续输入及无关草稿。取消未提交选择、关闭迟到的读取结果不产生目录写入。
- 旧版错误的跟随推断（拿模型ID与渠道ID比较）、只从当前DOM收集勾选值及跨渠道专用模型只存ID的做法不迁入。

## 模型目录接口的兼容增量

原接口继续有效。`POST /api/providers/fetch-models`、`POST /api/providers/models`、`DELETE /api/providers/models`可携带`expectedBaseUrl`。服务端对实际渠道地址规范化后比较，不匹配时409；fetch在向远端发送凭据之前核对。调用方没有该字段时保持原兼容语义。

`POST /api/providers/set-key`也支持该可选地址核对。当前渠道密钥编辑器使用这个入口，不再误改`api.apiKey`；切换渠道会清空输入和已显示明文，迟到的读取结果不重新显示。只有直连模式才显示直连密钥编辑器。

导入选择使用`POST /api/providers/models`的`onlyMissing:true`：只追加请求处理时仍不存在的ID，不覆盖弹窗期间另一方新建的模型名称/元数据。远端列表仅接收ID和展示名称，不把远端凭据或能力声明当作宿主配置。已有渠道的密钥保持宿主存储，不进入目录选择器。

专用模型新增的渠道字段与真实端点消费见[llm.target合同](architecture-composition.md#31-模型目标解析-llmtarget)。不显式绑定渠道的旧配置保持原端点语义；记忆与备选的显式目标不会被主调用的图片/视频切换覆盖。

## 追加式替换与边界

默认模块拆分为`panels/settings/model-catalog.js`、`model-picker.js`、`model-import.js`、`model-selector-view.js`及`model-catalog-data.js`。通过现有`ui.assets`可单独替换选择器，保留导入等其他默认能力。187用真实createApplication追加一个选择器文件，验证实际保存及默认导入独立工作。

当前渠道凭据编辑独立在`provider-credential.js`，同样是可替换的默认UI文件。

`openModelPicker({providers,current,title,onPick})`把`{provider,model}`交给`onPick`；第二参数可提供`isCurrent()`用于异步提交前检查选择器是否仍在。`openModelImport({provider,load,onApply})`的load只返回可选列表；只有确认才调用onApply。两者不自行获取令牌、访问宿主DOM或放宽RPC白名单。默认设置通过原配置表单和已声明API执行提交。

界面追加层属于管理员受信任启动组合。普通市场包不会自动取得该能力，也不会自动取得`llm.target`的全配置及密钥。188通过实际HTTP调用验证核心目标解析的追加替换和撤销回退；187与186验证真实UI、持久化、并发导入和取消。当前定向测试不代表整个项目已再次完整回归，完整状态以对应冻结运行终态为准。

## 凭据来源规则的修订

这部分明确修订旧R27无来源约束的全局回退，不复制“未知渠道/任意目标自动借用全局Key”的行为。选定渠道的真实调用、最小探针和模型发现只使用该渠道自身的Key；未配Key时允许匿名接口，不借用全局直连Key。直连请求仅在其配置来源内自动使用直连Key，用户明确为另一个目标填写新Key仍允许使用。账号池改变来源又没有提供Key时，不继承之前渠道的Key；显式空Key表示匿名。

保留只有渠道Key、端点位于主配置的旧数据；不能把缺少重复端点元数据的旧配置一律判为错误。SDK只覆写model时继承当前渠道，而明确指定不存在的渠道报错。实际完整凭据元组来源冲突时不向错误地址发送Key；主配置失败仍可使用用户明确声明的安全备选，错误的专用绑定则停止，不偷偷换其它渠道。

41保持旧Key优先级及仅主配置端点的有效情形；33保留显式新Key和同来源渠道Key/直连Key，并新增跨来源不外发的反例。两项初次失败与修正记录保留在`.qa-local/v04-parity-20261016`，不是删掉兼容测试换绿灯。189实际验证当前渠道写入、显示、三击清除、真实调用/探针/发现的密钥一致性及迟到明文隔离。

## 第三批：渠道编辑事务与字段冲突

`provider-editor.js`为独立默认UI文件，可用`ui.assets`替换。它只向`POST /api/providers/update`提交实际改动字段：`displayName`、`baseUrl`、模型ID数组`models`和可选的新`apiKey`。空白Key保留，清除仍是单独三击动作。未改动的目录和其它渠道不从旧表单回传。

接口按ID读取提交时当前配置；所有编辑须匹配打开时的端点，改名称/目录时再比对对应字段的原值。并发修改不同字段可合并，同字段冲突返回409且不部分写入。同ID模型的最新对象元数据和保留条目的别名由服务器保留。当前主渠道改址只同步api.baseUrl，不覆盖当前model或其它配置。元数据、端点、主绑定和新Key只调用一次所选config.update，先写临时文件并rename成功后才发布内存/事件。

`GET /api/providers`提供不透明`credentialRevision`，仅编辑新Key时用于比较；它以随机进程密钥做HMAC，覆盖此渠道已有的配置/内联/环境凭据来源。前端不会收到密钥散列或已有明文。进程重启或凭据变化时旧编辑提交会被拒绝，重新打开即可；它不代替原有请求认证/权限。set-key返回最新标记，让在当前弹窗明确清Key后仍能继续编辑。旧set-key等接口兼容，不能把这个新编辑接口的比较保证泛化为所有旧调用者都有CAS。

新增190覆盖真实UI单次联合提交、跨窗口新增邻居/目录保留、同字段/Key/端点冲突、不同行字段合并、保留对象元数据、显式清空目录、真实临时文件写失败后的内存/磁盘/事件原子性及重试、关闭等待中的编辑防迟到提交。实际追加单个编辑器文件后，默认模型管理仍独立可用；有头与无头通过。
