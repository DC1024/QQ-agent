# 损坏配置备份诊断迁移

本原子对应 `../develop/src/config.js` 的 `loadConfig()` 异常分支。旧版在改名成功后才报告备份位置，改名失败则单独报告备份失败，随后仍返回默认配置；后续保存可覆盖配置文件。v0.5 原默认实现吞掉 rename 异常后仍报告“已备份”，因此诊断可能与磁盘不符。独立坏 JSON fixture 的修前实测保留在 [baseline-result.json](../.qa-local/v04-parity-20261016/config245/baseline-result.json)：一次精确目标 rename 拒绝、没有备份、原件字节未变，但日志声称成功。

## 本次行为

仅调整默认 `runtime.config` 的 `load()` 异常分支：

- 只有 rename 成功才报告实际备份文件名。已有同时间戳备份使用递增后缀，不覆盖已存在的普通备份文件。
- rename 失败明确报告“备份失败”。原件仍存在时明确说明仍在原位、未改写；不能确认时如实提示检查磁盘。失败不制造空备份或成功回执。
- 诊断区分 JSON 语法错误与读取错误，只输出类别和受限文件系统错误码，不输出异常 message、配置原文或密钥。备份本身保留原始字节，需由使用者妥善保管。
- 明确提示首次加载采用默认配置、应及时保留或恢复原件，以及后续保存会覆盖全量 `config.json`。

这次没有增加写入冻结、自动恢复或新的修复接口。`load()` 仍返回当前内存对象：初次构造是默认值，重复加载失败时沿用现有内存值。读取失败也沿用原有尝试备份的行为，并不据此断言文件内容损坏。正常加载、迁移、秘密字段保留、原子写回和控制器 CAS 均不改变；备份失败后的正常 `update()` 仍可写入并覆盖原文件。

递增后缀用于处理加载时已经存在的名字；它不构成多个外部进程同时创建同一目标文件时的原子无覆盖保证，也不保证断电或磁盘故障后的恢复。

## 组合与验证

实现仍经由 `createApplication()` → 所选 `runtime.kernel` → 所选 `runtime.config` 工厂构造。没有新增固定构造入口或修改默认组件表。可信追加层可以完整替换或包装 `runtime.config`；完整替换的实现自行承担其诊断合同。

`node test/245-config-corrupt-diagnostic-test.mjs` 实际执行 10 组：7 组纯配置检查在独立子进程中完成，精确故障替身只作用于 fixture 的目标 `readFileSync` 或 `renameSync`，并在 finally 恢复；3 组复制真实生产代码，通过追加 replace、再 wrap、禁用两层恢复默认，运行真实应用和随机 loopback HTTP。消费者验证包含 `/api/config`、`/api/logs`、正常恢复保存、密钥保留及 `/api/blocklist-raw` 陈旧版本 409 与磁盘不变，并检查退出后 scheduler 与实例锁清理。

专项不打开浏览器，不连接 QQ、账号、外部模型或远端 HTTP，不读取用户数据或已安装扩展实现。实际逐组日志和带时间戳结果在 [.qa-local/v04-parity-20261016/config245](../.qa-local/v04-parity-20261016/config245/)。首次默认沙箱执行因 Node 子进程 EPERM 未完成，失败结果保留；获准的隔离执行随后真实 exit 0。另运行原 `03-config` 回归核对既有默认值、加载、写回和脱敏行为。专项通过不代表新完整回归已经完成。
