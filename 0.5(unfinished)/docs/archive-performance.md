# 存档增长后的性能优化（2026-10-19）

用户反馈：存档增多后启动、切换页签和部分按钮变慢，要求保留规格书中的 DeepSeek Harness 装配与可替换组件边界。本轮同时完成此前“社区”改为“我的”及人物图标/选中动画重绘。

## 主要开销与算法

1. 原存档接口先读取并投影全部消息，然后才分页；每条引用又线性查找源消息。多引用历史可产生 O(N²) 工作。默认消息仓新增可选的 page(chatKey,{limit,offset,beforeId})：先定位和截取当前页，再解析引用。协议消息ID用惰性 Map 索引，游标用二分查找；已建索引后的有序历史分页为 O(log N + K)。旧数据ID无序时按原数组顺序过滤，不重排、不假定本地ID连续。首次解析单文件和建索引仍是 O(N)。
2. 普通聊天列表复用摘要。冷文件按 size/mtime/ctime/inode 检验版本，未加载的文件只保留摘要，不缓存整段消息；已加载数据用弱引用派生缓存，写入、撤回、删除、标读及严格写失败回滚均失效。模型上下文读取保持原失效追踪，返回DTO不能修改缓存本身。
3. 启动恢复会话改为每批至多8个文件、约8ms时间预算，批间用setImmediate让HTTP和桌面事件继续处理。单文件读盘/解析不可抢占，因此预算不是单次阻塞的硬上限。恢复完成后列表不再重复解析磁盘索引。
4. 历史用量按会话幂等重放。健康且未变化的已归档记录不再克隆、聚合和写回整个日档；计量、工具、状态、渠道、活动等改变及失败重试仍走原事务。活动对象保存独立副本，不能因活对象同址修改误判“未变化”。启动恢复也只在归档基线变化时重写会话文件。
5. 用量统计优先复用所选会话仓的已加载对象，减少反复读取完整流水文件。

消息JSON结构、本地ID、撤回和引用语义、同步原子落盘、会话peek活对象/get副本、计费增量和错误重试语义保持。没有更换数据库、重排或裁剪历史，也不自动删除用户存档。超大单文件的首次读取以及每次消息同步落盘仍受JSON解析/序列化与磁盘速度影响。

## 架构边界

已读取 ../dsh-spec/DSH-ARCH.md、SPEC配套notes/12-data.md 和当前 docs/architecture-composition.md。优化位于既有 data.messages、data.sessions、data.usage 默认工厂及 console.routes 内，仍通过 createApplication/defaultComponents 选取；未新增固定宿主旁路。

page 为宿主可选扩展，不新增SDK权限。路由只调用当前所选消息仓；替换仓没有page时继续调用其原recent接口完成同口径分页，不偷偷构造默认仓。271在真实临时应用/HTTP上验证追加包装器接管分页，以及仅有旧接口的替换仓被继续消费；171/174验证整体组件替换装配。新增缓存没有独立定时器；会话恢复的批处理在原stop中取消。
